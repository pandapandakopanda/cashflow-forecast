# Cashflow Forecast — REST API contract (MVP)

**Статус:** утверждённый контракт для реализации.  
**Владелец контракта:** аналитик / условная backend-команда.  
**Для разработчика:** не нужно придумывать поля, URL, формы ответов или HTTP-коды. Реализовать сервер по этому документу; фронтенд интегрировать по нему же. При расхождении документа и требований сначала уточнить и изменить контракт, а не молча создавать вторую версию.

Связанные документы: [SPEC.md](../SPEC.md), [FIN-02](https://github.com/pandapandakopanda/cashflow-forecast/issues/2).

## 1. Общие соглашения

- Base URL локальной разработки: `http://localhost:3001/api`. Клиент использует переменную окружения/прокси; не привязывается к адресу продакшена.
- `Content-Type: application/json; charset=utf-8` для всех запросов с телом и JSON-ответов.
- Идентификаторы — непрозрачные строки, создаваемые сервером (клиент не извлекает из них бизнес-смысл).
- Деньги передаются **только в целых копейках**: `amountCents`, `openingBalanceCents`. В UI показываются рубли и копейки. Тип операции задаёт знак: `income` / `expense`. `amountCents` всегда строго положительно.
- Диапазон для положительной суммы: от `1` до `99999999999` копеек включительно. Начальный остаток: целое от `-99999999999` до `99999999999`.
- Даты — календарные строки `YYYY-MM-DD`; месяцы — `YYYY-MM` (нужно проверять **реальные** числа дней). Никаких ISO datetime, UTC и конвертации таймзон в бизнес-логике.
- Название операции: строка, после trim от 1 до 120 символов. Неизвестные поля в запросе отклонять ошибкой валидации.
- Время выполнения и сортировка при одинаковой дате не влияют на остаток.
- Для MVP сервер ведёт один локальный демонстрационный профиль. **Это не API для общего публичного использования без изоляции данных.** Если развернётся публичная демоверсия, сначала потребуется отдельное анонимное пространство данных для каждого посетителя или режим только для чтения. Не вводить сюда реальные личные финансовые данные.

### Типы (смысловые, без навязывания языка кода)

**Transaction:** `{id: string, title: string, type: "income"|"expense", amountCents: integer, date: "YYYY-MM-DD"}` — разовая запись.

**RecurringRule:** `{id: string, title: string, type: "income"|"expense", amountCents: integer, dayOfMonth: integer(1..31), startMonth: "YYYY-MM"}`. Правило действует во всех месяцах начиная с `startMonth` включительно, пока не удалено. В месяце с меньшим числом дней событие происходит в последний день.

**MonthOperation (элемент массива месячного плана):**
- общие поля: `id`, `source` (`"oneTime"` или `"recurring"`), `title`, `type`, `amountCents`, `date`;
- для `source: "oneTime"`: `id` равен ID разовой операции, без `recurrence`;
- для `source: "recurring"`: `id` — стабильный идентификатор вхождения одного правила в одном месяце; поле `recurrence: {ruleId, dayOfMonth, startMonth, overridden}`. `overridden=true` значит, что именно это вхождение изменено исключением;
- пропущенное исключением (`skip`) регулярное вхождение **не включается** в список операций данного месяца.

**MonthPlan:** `{month, revision, openingBalanceCents, operations}`, где `month` — `YYYY-MM`, `revision` — целое число >= 0, `openingBalanceCents` — целое число или `null`, `operations` — массив MonthOperation, сортированный по дате, затем по `id`.

**Версия (revision):** для простого MVP используется общий монотонно растущий номер версии финансовых данных **профиля**. Любое успешное изменение плана/операций/правила увеличивает его на 1 (или один раз на атомарный пакет). Поэтому изменение другого месяца также может сделать эксперимент устаревшим — это сознательное упрощение. Применение сценария проверяет совпадение присланного `revision` с текущим.

## 2. Ошибки

Единый JSON-формат (для ответов 4xx/5xx):

    {
      "error": {
        "code": "VALIDATION_ERROR",
        "message": "Сумма должна быть больше нуля",
        "details": [
          {"field": "amountCents", "message": "Ожидается целое число от 1 до 99999999999"}
        ]
      }
    }

`details` — массив, может быть пустым. `field` — имя поля или путь внутри массива (`operations[1].date`).

| HTTP | code | Когда |
| --- | --- | --- |
| 400 | INVALID_MONTH | Неверный сегмент месяца в URL (например, 2026-13) |
| 400 | INVALID_JSON | Не удалось разобрать тело JSON |
| 422 | VALIDATION_ERROR | Некорректные поля, даты, суммы, ID/дубликаты внутри пакета |
| 404 | NOT_FOUND | Не существует указанный ID операции/правила |
| 409 | REVISION_CONFLICT | Версия плана устарела (для применения сценария) |
| 500 | INTERNAL_ERROR | Непредвиденная ошибка без выдачи SQL/стека клиенту |

Ошибки валидации не изменяют БД. Ответ `204 No Content` не содержит JSON.

## 3. Проверка сервера

### GET /api/health

**200 OK**

    {"status":"ok"}

Отдельная бизнес-логика и подключение SQLite для этого маршрута не требуются.

## 4. Месяц и начальный остаток

### GET /api/months/:month

Пример: `GET /api/months/2026-11`.

**200 OK** — даже если записей ещё нет.

    {
      "month": "2026-11",
      "revision": 7,
      "openingBalanceCents": 1000000,
      "operations": [
        {
          "id": "tx_101",
          "source": "oneTime",
          "title": "Подработка",
          "type": "income",
          "amountCents": 300000,
          "date": "2026-11-05"
        },
        {
          "id": "occ_rule_12_2026-11",
          "source": "recurring",
          "title": "Кредит",
          "type": "expense",
          "amountCents": 150000,
          "date": "2026-11-30",
          "recurrence": {
            "ruleId": "rule_12",
            "dayOfMonth": 31,
            "startMonth": "2026-09",
            "overridden": false
          }
        }
      ]
    }

Если остаток не задавали и нет записей, ответ: `{"month":"2026-11","revision":0,"openingBalanceCents":null,"operations":[]}` (фактическая ревизия может быть выше, если ранее менялись другие месяцы).

### PUT /api/months/:month/opening-balance

**Запрос:**

    {"openingBalanceCents": -250000}

`openingBalanceCents` обязателен, целое число, включая ноль и отрицательные суммы, в указанном выше диапазоне. `null` **не разрешён** в этой мутации; возвращать настройку в «не указано» через UI в MVP не требуется.

**200 OK:**

    {"month":"2026-11","openingBalanceCents":-250000,"revision":8}

Валидация: 400 для неверного месяца, 422 для неправильной суммы. После изменения GET плана отражает новое значение.

## 5. Разовые операции

### POST /api/transactions

**Запрос:**

    {
      "title": "Аптека",
      "type": "expense",
      "amountCents": 12345,
      "date": "2026-11-12"
    }

Все четыре поля обязательны. Дата — любая настоящая календарная дата, не ограничивается текущим месяцем.

**201 Created:**

    {
      "transaction": {
        "id": "tx_102",
        "title": "Аптека",
        "type": "expense",
        "amountCents": 12345,
        "date": "2026-11-12"
      },
      "revision": 9
    }

### PATCH /api/transactions/:id

В запросе **как минимум одно** из полей: `title`, `type`, `amountCents`, `date`. Переданные поля проверяются, остальные остаются прежними. Пустой объект — 422.

**Запрос:**

    {"amountCents": 15000, "date": "2026-12-02"}

**200 OK:** такой же объект ответа, как у POST, с сохранённым ID и новой ревизией.

### DELETE /api/transactions/:id

**204 No Content** (не возвращать JSON). Отсутствующая операция — 404.

Для frontend: после создания/изменения/удаления обновить соответствующие кэши месячных планов RTK Query. Если `date` изменяется на другой месяц, нужно актуализировать оба месяца.

## 6. Ежемесячные операции

### GET /api/recurring-rules

**200 OK:**

    {
      "items": [
        {
          "id": "rule_12",
          "title": "Кредит",
          "type": "expense",
          "amountCents": 150000,
          "dayOfMonth": 31,
          "startMonth": "2026-09"
        }
      ]
    }

Используется клиентом при изменении **правила целиком** (в GET месячного плана приходят вхождения, не полные сущности правил).

### POST /api/recurring-rules

**Запрос:**

    {
      "title": "Зарплата",
      "type": "income",
      "amountCents": 9500000,
      "dayOfMonth": 10,
      "startMonth": "2026-11"
    }

Все поля обязательны. `dayOfMonth` — целое 1..31. `startMonth` — действительный месяц.

**201 Created:**

    {
      "rule": {
        "id": "rule_13",
        "title": "Зарплата",
        "type": "income",
        "amountCents": 9500000,
        "dayOfMonth": 10,
        "startMonth": "2026-11"
      },
      "revision": 10
    }

### PATCH /api/recurring-rules/:id

Передать как минимум одно из полей `title`, `type`, `amountCents`, `dayOfMonth`, `startMonth`; остальные сохраняются без изменений.

**Запрос:** `{"dayOfMonth":15}`

**200 OK:** объект `{"rule": {...все поля...}, "revision": 11}`. Изменение правила действует на **все** месяцы начиная с действительного `startMonth` (прошлые/будущие в рамках сохранённой модели); для точечной правки месяца используйте исключения ниже.

### DELETE /api/recurring-rules/:id

**204 No Content**. Правило и связанные с ним исключения удаляются; после этого вхождения не возвращаются ни в одном месяце. Отсутствующий ID — 404.

### PUT /api/recurring-rules/:id/exceptions/:month

Создаёт или заменяет исключение для **одного** вхождения правила в **одном** месяце. Выбранный месяц должен быть не раньше `startMonth`.

**Вариант 1: исключить вхождение**

    {"action": "skip"}

**Вариант 2: переопределить вхождение**

    {
      "action": "override",
      "title": "Кредит — досрочно",
      "type": "expense",
      "amountCents": 150000,
      "date": "2026-11-20"
    }

При `override` все четыре поля обязательны, `date` должна лежать в указанном `:month`. При `skip` дополнительных полей нет.

**200 OK:**

    {
      "exception": {
        "ruleId": "rule_12",
        "month": "2026-11",
        "action": "override",
        "title": "Кредит — досрочно",
        "type": "expense",
        "amountCents": 150000,
        "date": "2026-11-20"
      },
      "revision": 12
    }

Для `skip` ответ содержит `ruleId`, `month`, `action:"skip"` и `revision`, но не поля операции. Изменяется **только** выбранный месяц; остальные вхождения остаются прежними.

### DELETE /api/recurring-rules/:id/exceptions/:month

**204 No Content**. Удаляет существующее исключение и восстанавливает обычное вхождение правила в этом месяце. Отсутствующее правило или исключение — 404.

## 7. Эксперимент «Что, если?»

### Правило создания сценария на frontend

Клиент получает `GET /api/months/:month` и копирует `openingBalanceCents`, `revision`, `operations` в **обычный Redux slice**. Это локальная копия; никакие mutations при её редактировании не отправляются.

Для новых операций клиент генерирует локальный `clientId` (например `draft-1`), **не** серверный ID. При изменении операции сохранить её `id` и `source`. Удалить операцию из локального массива — значит исключить её из итогового месячного плана.

### POST /api/months/:month/apply-scenario

**Запрос — полный итоговый снимок одного месяца:**

    {
      "revision": 12,
      "openingBalanceCents": 1000000,
      "operations": [
        {
          "source": "oneTime",
          "id": "tx_101",
          "title": "Подработка",
          "type": "income",
          "amountCents": 300000,
          "date": "2026-11-05"
        },
        {
          "source": "recurring",
          "id": "occ_rule_12_2026-11",
          "title": "Кредит",
          "type": "expense",
          "amountCents": 150000,
          "date": "2026-11-20"
        },
        {
          "source": "new",
          "clientId": "draft-1",
          "title": "Покупка",
          "type": "expense",
          "amountCents": 200000,
          "date": "2026-11-18"
        }
      ]
    }

- `revision` обязателен: число версии, полученное при начале эксперимента.
- `openingBalanceCents` обязателен и должен быть **целым числом**; если на момент начала эксперимента был `null`, пользователь должен сначала указать начальный остаток в эксперименте для применения. Пустой основной месяц можно открыть и отредактировать, но отправлять `null` нельзя.
- `operations` — полный список **оставшихся** операций месяца, включая неизменённые, отредактированные и новые. Пустой массив допустим.
- `source:"oneTime"`: обязательный `id` существующей разовой операции и её итоговые поля.
- `source:"recurring"`: обязательный `id` существующего регулярного вхождения этого месяца и итоговые поля. Сервер самостоятельно узнаёт `ruleId` по идентификатору, не доверяя `recurrence` из клиента.
- `source:"new"`: обязательный уникальный в пределах запроса `clientId` и итоговые поля. Сервер создаёт **разовую** операцию. Тип `new` не создаёт новое ежемесячное правило.
- Для **всех** элементов дата должна относиться к выбранному месяцу. Все идентификаторы в одном запросе уникальны; чужие/неизвестные ID, неправильные даты и поля — 422.
- Если существующая разовая операция отсутствует в снимке, она удаляется **только если её дата находится в этом месяце**. Если отсутствует регулярное вхождение, создаётся исключение `skip` для этого месяца.
- Если регулярное вхождение присутствует, но изменено, создаётся/обновляется исключение `override` для этого месяца. Если его итоговые поля равны исходному правилу, прежнее исключение удаляется.
- Проверять и применять **весь** снимок в одной SQLite-транзакции. Ошибка где угодно означает rollback, без частичного сохранения.
- Прежде любых изменений сравнить `revision` с текущей версией профиля. Несовпадение: `409 REVISION_CONFLICT`, данные не изменяются.

**200 OK:** возвращает **полный MonthPlan** по формату GET, с обновлённой `revision` и серверными ID у новых операций. Например, та же схема `{month,revision,openingBalanceCents,operations}`, что описана в разделе 4.

**409 Conflict:**

    {
      "error": {
        "code": "REVISION_CONFLICT",
        "message": "Финансовый план изменился. Обновите данные и создайте эксперимент заново.",
        "details": []
      }
    }

Клиент **не** удаляет эксперимент при 409/ошибке сети/5xx; пользователь должен видеть ошибку и иметь возможность вручную решить, что делать дальше. Только после 200 и актуализации RTK Query можно завершить эксперимент.

## 9. Приёмка API

- Тестовый локальный сервер реализует указанные endpoints без расхождений по JSON-полям/HTTP-статусам.
- Отсутствующий баланс и заданный 0 — разные состояния.
- Короткие месяцы/високосные годы дают правильные даты вхождений.
- Разовая отмена регулярного платежа не меняет глобальное правило.
- При отклонении данных изменения в БД отсутствуют; при конфликте версии возвращается 409.
- Применение эксперимента атомарно, включая удаление, изменение и создание операций.
- Нет «догадок» со стороны frontend: при реализации RTK Query данные типизируются **по данному документу**.

> Это учебный контракт для небольшого приложения, не спецификация для реальных банковских операций. Никаких банковских данных или финансового совета.
