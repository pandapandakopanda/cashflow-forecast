# Cashflow Forecast — спецификация MVP

**Версия:** 1.0 (зафиксированный объём)  
**Цель:** приложение для прогноза денежных остатков по дням выбранного календарного месяца и проверки финансовых решений в режиме «Что, если?».  
**Аудитория:** один пользователь/демонстрационный профиль, без регистрации и банковских интеграций.  
**Разработчик:** самостоятельно реализует решения, спецификация определяет поведение, но не навязывает структуру компонентов.

## 1. Границы MVP

Входит:
- Выбор календарного месяца и ввод начального остатка этого месяца.
- Доходы и расходы: разовые и ежемесячно повторяющиеся.
- Просмотр операций выбранного месяца, создание, изменение и удаление.
- Расчёт остатка после операций каждого дня, минимального и конечного остатков; предупреждение о днях с отрицательным остатком.
- График прогноза (SVG, без Canvas).
- Один альтернативный сценарий «Что, если?» — независимая копия операций выбранного месяца; локальные изменения, сравнение графиков и показателей, сброс и применение к основному плану.
- REST API Node.js + Express + SQLite, frontend React + TypeScript strict + Redux Toolkit + RTK Query + Tailwind CSS, формы React Hook Form + Zod, тесты и CI.

Не входит:
- Регистрация, роли, авторизация, банковские интеграции, импорт банковских выписок, категории/аналитика по категориям, несколько валют, несколько сценариев одновременно, еженедельные и произвольные повторы, прогноз за 30/60/90 дней, передача баланса между месяцами, собственный движок диаграмм, реальное финансовое консультирование.

## 2. Термины и данные

- **Месяц**: строка YYYY-MM; даты операций — YYYY-MM-DD, как календарные даты (без преобразования часовых поясов).
- **Сумма**: положительное число денежных единиц; тип операции отдельно задаёт знак (+ доход, − расход). В вычислениях используются целые копейки, отображение — рубли.
- **Начальный остаток**: сумма на начало первого дня выбранного месяца, может быть положительной, нулевой или отрицательной. Задаётся отдельно для каждого месяца, не переносится автоматически.
- **Разовая операция**: название, тип, сумма, дата, идентификатор.
- **Ежемесячная операция**: название, тип, сумма, день месяца (1–31), месяц начала повторений (YYYY-MM) и идентификатор правила. Применяется с месяца начала включительно.
- **Вхождение регулярной операции**: вычисленное событие в конкретном месяце; имеет стабильный идентификатор в пределах этого месяца.
- **Исключение**: отмена или замена одного вхождения регулярной операции только в одном выбранном месяце. Исходное правило не меняется.
- **Основной план**: данные, сохранённые сервером; **эксперимент**: локальная полная копия вычисленных операций одного месяца, не меняющая сервер до применения.

## 3. Бизнес-правила

### Месяц и баланс
1. При открытии пользователь видит текущий календарный месяц. Может переключить месяц назад/вперёд.
2. Если для месяца нет начального остатка, отображается незаполненное состояние и предлагается ввести сумму (в том числе 0); не считать отсутствие ввода подтверждённым нулём.
3. Изменения начального остатка основного плана сохраняются сервером. В эксперименте можно менять начальный остаток только локально.
4. Дневной остаток: начальный остаток + суммы всех доходов со дня 1 по текущий день − суммы всех расходов за тот же интервал. Операции одной даты учитываются в сумме независимо от порядка отображения.
5. Итог месяца — остаток на последний день; минимум месяца — минимальный из рассчитанных **дневных итоговых** остатков в пределах месяца. Отдельно выделяются дни, чей остаток ниже нуля.
6. Прогноз включает весь календарный месяц, даже если дата в будущем или прошлом; приложение показывает расчёт **по введённому плану**, а не фактический банковский баланс. Названия «прогноз» и «план» не должны вводить в заблуждение.

### Операции
7. Название обязательно, непустое после обрезки пробелов; сумма строго больше нуля; тип доход или расход; дата разовой операции действительна.
8. Ежемесячная операция на 29, 30 или 31 число в более коротком месяце приходится на **последний день** месяца.
9. Повторения действуют со стартового месяца включительно; операции до него не создаются. Изменение/удаление регулярного правила влияет на все месяцы действия правила (в том числе прошедшие); изменение только одного месячного вхождения выполняется через исключение.
10. Для редактирования только выбранного вхождения регулярной операции (в частности в эксперименте) создаётся исключение на один месяц; первоначальное правило остаётся прежним.
11. После создания/изменения/удаления основного плана данные загружаются заново или обновляются через механизмы кэша RTK Query; состояние UI должно соответствовать серверу.

### Эксперимент «Что, если?»
12. Эксперимент создаётся кнопкой «Создать эксперимент» для активного месяца как полная независимая копия разрешённых операций месяца и его начального остатка.
13. В эксперименте можно изменять сумму, дату (в пределах того же месяца), название, тип, добавлять разовые операции, исключать существующие; изменять начальный остаток. Добавленные в эксперименте операции рассматриваются как **разовые в выбранном месяце**, не как новые ежемесячные правила.
14. Основной план остаётся неизменным до явного нажатия «Применить» и подтверждения. Сброс восстанавливает актуальный основной план.
15. При попытке переключить месяц с несохранённым экспериментом нужно предупредить о потере изменений; при подтверждении эксперимент закрывается.
16. При сравнении отображаются оба прогноза, их минимальный и конечный остатки и разница. В один момент допускается **один** эксперимент.
17. Применение выполняется атомарной серверной операцией: изменения разовых операций сохраняются для месяца, а изменения ежемесячных вхождений — как исключения **только этого месяца**. Правила повторения на другие месяцы не меняются. При ошибке сервер не сохраняет частичный результат; эксперимент остаётся доступным для повторной попытки.
18. Если основной план был изменён на сервере после создания эксперимента, перед применением сервер отклоняет устаревшую версию с конфликтом; интерфейс предлагает пересоздать сценарий после обновления данных (без автоматического затирания изменений).

## 4. Экраны и поведение

- **Основной экран:** заголовок с месяцем; поле начального остатка; итоговые показатели; график; список операций и форма создания/редактирования.
- **Режим эксперимента:** явно обозначен, визуально отличаются основная и альтернативная линии прогноза; редактор экспериментальных операций; «Сбросить», «Применить».
- **Состояния:** загрузка, пустой месяц/нет операций, ошибка API с повтором, успешное сохранение, предупреждение о риске отрицательного остатка; доступная навигация клавиатурой и читаемые подписи.

## 5. Архитектура и API — обязанности

- **Node.js/Express + SQLite:** валидация входящих данных; работа с месяцами, разовыми операциями, правилами повторения и исключениями; транзакционное применение эксперимента. Нельзя доверять только браузерной валидации.
- **RTK Query:** получение месячного плана и мутации основного плана, кэш, invalidation tags, отображение загрузки и ошибок. Не дублировать API-кэш в обычных slices.
- **Redux Toolkit slices:** активный месяц, экспериментальный сценарий и его локальные изменения.
- **Чистые функции/селекторы:** построение дневных остатков, итогов, минимумов и разницы сценариев. Расчёты тестируются без React.
- **React Hook Form + Zod:** формы и пользовательская валидация; Tailwind — стили; график на SVG (например, Recharts), без Canvas.

**Ответственность за API-контракт:** готовый документ [docs/API.md](docs/API.md) подготовлен аналитиком как условной backend-командой **до начала реализации**. В нём зафиксированы URL, методы, структуры запросов и ответов, поля, правила валидации, примеры и HTTP-ошибки. Задача [FIN-02](https://github.com/pandapandakopanda/cashflow-forecast/issues/2) теперь посвящена **реализации** общей валидации и обработки ошибок по этому готовому контракту. Ни frontend, ни backend-разработчику не нужно проектировать контракт заново. Если выявлен пробел или противоречие, аналитик уточняет документ; изменение поведения согласуется до разработки.

Минимальные ресурсы API: месячные остатки, разовые операции, правила ежемесячных операций, исключения отдельных вхождений и атомарное применение месячного сценария. Суммы и правила дат определяются данной спецификацией; конкретные поля, параметры и статусы уже описаны в [docs/API.md](docs/API.md).

## 6. Публичная демоверсия и безопасность

- Не вводить и не публиковать реальные финансовые данные. В README и интерфейсе — явная пометка «демонстрационный/учебный финансовый прогноз, не банковские данные».
- Для публичной версии данные разных посетителей не должны смешиваться и перезаписываться. Допустимое простое решение — отдельный анонимный демо-профиль/сессия на сервере (без регистрации), ограничение объёма записей и очистка старых демо-данных. Если безопасную изоляцию и постоянное хранилище не удастся развернуть, не публиковать общую редактируемую базу; оставить локально запускаемый API и честно указать это в README.
- Не хранить секреты в Git; документировать переменные окружения; ошибки API не раскрывают внутренние детали.

## 7. Критерии готовности MVP

- Основной план переживает перезагрузку клиента и перезапуск сервера (при сохранённой БД).
- Разовые и ежемесячные операции правильно отражаются в месячном прогнозе, включая 29–31 числа.
- Все рассчитанные суммы согласованы между списком, показателями и графиком.
- Эксперимент не изменяет основной план до применения; сброс и успешное применение работают корректно; ошибки не дают частично сохранить изменения.
- Формы валидируются и с клиента, и на сервере; загрузка и ошибки отображаются.
- Есть тесты для критичных вычислений и API, минимальный UI/E2E тест; проверки запускаются в CI.
- Есть README с установкой, запуском, архитектурой, возможностями и скриншотами; код доступен в публичном GitHub-репозитории.

## 8. Условности управления задачами

- Каждую функцию реализовать отдельной GitHub Issue с конкретными сценариями, перечнем полей, состояниями интерфейса, критериями приёмки и примерами проверок; подробные задачи доступны в [GitHub Issues](https://github.com/pandapandakopanda/cashflow-forecast/issues).
- Рабочий порядок: **Backlog → Ready → In progress → In review → Done**.
- Работа разработчика самостоятельная: аналитическая задача описывает ожидаемое поведение, но не содержит готового кода.
- Изменения объёма после фиксации MVP — в отдельную будущую версию, не в текущий backlog.
